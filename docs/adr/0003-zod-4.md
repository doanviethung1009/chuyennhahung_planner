# ADR 0003 — Upgrade zod to 4.x

🇻🇳 Bản tiếng Việt: [0003-zod-4.vi.md](0003-zod-4.vi.md)

- **Status:** Accepted
- **Date:** 2026-11-09
- **Owner:** system-architect

## Context

`zod` validates every external input in this system — the 17 Travel Content admin
routes and the whole Planner surface — so it sits on the trust boundary rather than
beside it.

The pinned 3.25.76 is subject to
[GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), high
severity: validating an **oversized constrained collection** can exhaust memory. The
codebase uses that exact shape on request input, for example
`z.array(z.string()).min(n).max(50)` in `src/server/content/schemas.ts`.

The advisory's affected range is `<4.6.6`, which covers **every** 3.x release. There is
no patched 3.x, so the choice was never "patch or upgrade" — it was "upgrade, mitigate,
or accept".

What was already true before this ADR: [#12](https://github.com/doanviethung1009/chuyennhahung_planner/pull/12)
capped request bodies at 256 KiB in `parseJsonBody`, before parsing or validation. That
bounds the advisory, because an oversized collection can no longer reach the validator.
It does not remove it — the library is still vulnerable, the cap is simply in front of
it — and `npm audit` still reported the advisory.

What we did not know going in: how much of a v3 → v4 migration this codebase actually
needed. The published breaking changes are substantial in general, so the cost had to be
measured rather than assumed.

## Decision

Upgrade to `zod@^4.6.7` and migrate the two deprecated call sites it surfaced.

The measured cost turned out to be two lines:

| Site | Before | After |
|---|---|---|
| `src/server/content/schemas.ts` | `z.string().datetime()` | `z.iso.datetime()` |
| `src/server/content/http.ts` | `parseJsonBody<S extends z.ZodTypeAny>` | `<S extends z.ZodType>` |

Neither was forced — both old forms still work in 4.x — but both are deprecated, and
leaving them would hand the next major upgrade a bill for no benefit.

`z.iso.datetime()` was checked for equivalence before the swap, across nine inputs
including a UTC instant with and without milliseconds, a bare date, a `+07:00` offset
and a space-separated form: **zero behavioural differences, and the same error
message**. The API contract did not move.

The 256 KiB body cap from #12 stays. It is not redundant: it bounds *any* oversized
payload, not only the collection shape this advisory describes, and it is what keeps
the guarantee if a future zod regresses.

## Options considered

| Option | For | Against |
|---|---|---|
| **Upgrade to 4.x (chosen)** | Removes the advisory rather than fencing it; `npm audit --omit=dev` goes to **0**; migration measured at two deprecated lines, 312 tests green with no behavioural change | A major bump on the library every trust boundary depends on; commits us to 4.x's error-shape and API surface |
| Keep 3.x, rely on the #12 body cap | No migration risk, no diff | The advisory stays open and keeps appearing in every audit. The cap is in front of the bug, not a fix for it, so any path that validates a large collection *without* going through `parseJsonBody` would be unprotected — a future endpoint could reintroduce the exposure silently |
| Keep 3.x and suppress the advisory | Quiet audit output | Dishonest. A suppression records "we looked", not "we fixed", and the next reader cannot tell the difference |

The runner-up was keeping 3.x behind the body cap. It lost on one point: the cap
protects the current call sites, not the library, so it relies on every future endpoint
remembering to route through `parseJsonBody`. Removing the vulnerability does not rely
on anyone remembering anything.

## Consequences

**Easier.** Production dependencies audit clean (`npm audit --omit=dev` → 0). The
validator at the trust boundary no longer has a known memory-exhaustion path. Current
zod documentation now matches the installed version, which it did not before.

**Harder, and what this commits us to.** We are on 4.x now, which means:

- The error shape is 4.x's. `src/server/content/http.ts` maps `issue.path.join('.')` and
  `issue.message` into our own `FieldIssue`, and those strings reach API clients in the
  `issues` array of a 422. Any future zod minor that changes a message changes our
  response text. It is covered by tests that assert issue *paths*
  (`tests/travel-content-api.test.ts`, `tests/planner-api.test.ts`) — paths, not
  messages, so a message change would pass CI and surface to clients unnoticed.
- `z.iso.*` and `z.ZodType` are 4.x spellings. Reverting to 3.x means reverting both
  edits, not only the version range.
- Dev dependencies still pin zod 3.x transitively (`chromium-bidi` under
  `puppeteer-core`), so two major versions coexist in `node_modules`. Harmless — nothing
  shared crosses that boundary — but `npm audit` without `--omit=dev` will keep
  reporting zod until `puppeteer-core` is upgraded.

**To reverse:** restore `zod@^3`, revert the two call sites, and accept the advisory
again. The body cap would be the only protection, which is the position this ADR argues
against.

## Follow-up

- Code: `package.json`, `package-lock.json`, the two call sites above. Done in this change.
- Documents: no HTTP contract change, so `docs/travel-content-api.*` is unaffected.
  `.claude/context/project-context.md` records the version and is updated.
- **Worth the owner's attention:** nothing asserts zod's error *messages*, only paths.
  If the wording in a 422 `issues` entry is part of what clients rely on, that deserves
  a test pinning it. Flagged rather than added, because whether those strings are
  contract or incidental is the owner's call.
- Still outstanding and not addressed here: the 19 dev-only advisories.
  `vitest@5` cannot run until Node rises above Vite 7's 20.19 floor — recorded in
  `.claude/rules/05-git-governance.md`.

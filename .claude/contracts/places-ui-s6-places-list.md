# Task Contract: PLACES-UI-S6 `/places` list with search and filter (WEB-1)
- Class: **L** (public API behaviour added, shared `ListQuery`/repository, new public route, sitemap) · Branch: `feat/places-list` · Phase: none (Places UI, outside the Phase numbering; owner approved 2026-11-18, decisions 7 and 8 in [core-completion-index.md](core-completion-index.md)). Contract S1 ([places-ui-s1-public-places.md](places-ui-s1-public-places.md), DONE) is **not edited**.
- Desired outcome: a visitor can browse all places at `/dia-diem` (EN `/places`), search by name or location, and filter by destination and category, with paging — instead of reaching a place only through a destination page.
- Scope IN:
  - **API (backward compatible):** optional `q` on `GET /api/travel/places`. Omitted `q` = today's behaviour exactly. `q` is trimmed, 1–80 characters after trim (longer → 422 like other bad queries), treated purely as data: matched with a plain case- and diacritic-insensitive substring test in code (no regex built from input, no SQL/LIKE wildcard passed to a store). Vietnamese folding must handle `đ`/`Đ` (NFD alone does not): reuse or extract the folding in `src/lib/slug.ts` (P07-22) into a shared pure helper, do not copy it. Matched fields: `name` (vi, en), `location` (vi, en), and `category` label is NOT matched (category is a filter). Search runs **before** pagination (`limit`/`offset`). Add `q` to `listQuerySchema` only as an optional field and read it in `parseListQuery`; `listPlaces` applies it; every other list endpoint ignores it.
  - **Page:** `/places` (add `'/places': { vi: '/dia-diem', en: '/places' }` to `src/i18n/routing.ts`), server-rendered from `searchParams` (`q`, `destination`, `category`, `page`), page size 24, links for paging as real `<a>`; a plain GET `<form>` for search (works without JavaScript), filters as links or a `<select>` inside the same form; empty state, result count, "clear filters"; place cards reuse the existing public place card/section markup. One `<h1>`, ordered headings, visible focus, ≥44px targets, VI/EN messages.
  - **SEO/privacy:** list pages with `q`, filters or `page > 1` are `noindex, follow` with canonical to `/places`; the unfiltered first page is indexable; add `/places` (both locales) to `src/app/sitemap.ts`; `q` is never logged or echoed unescaped.
  - Link in: from the destinations index/section and the footer or nav only if one existing component already lists sections (state which in the handoff); no new navigation component.
  - Tests: pure helper (folding, matching incl. `đ`), repository `listPlaces` with `q` before paging, `q` bounds (422), omitted `q` unchanged, route test for `GET /api/travel/places?q=`, page test (routing map, sitemap entry, noindex rule), i18n parity, docs.
  - Docs: `docs/features/places.md` + `.vi.md` (new "list" section), `docs/travel-content-api.*` (new `q` parameter), `docs/architecture.*` only if the route map is listed there; ADR 0026 gets an amendment note (both languages) for the new list route — do not renumber.
- Scope OUT: new fields on places, publish/archive state for places (none exists), full-text engine, autocomplete, sorting options, ratings filter, map view, any admin change, any Planner/community code, affiliate. No change to S1, S2, S3 or S5 behaviour.

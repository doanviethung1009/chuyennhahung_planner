# Task Contract: password-google-sign-in — Planner sign-in with email/password and Google
- Class: XL (moves the authentication trust boundary; new PII in the planner store)
- Desired outcome / user impact: staff sign in with email + password (operator-created, temporary password, forced change); anyone signs in with Google, linking an existing account by verified email or creating a `member`-equivalent account on first sign-in. Access-token sign-in keeps working.
- Scope IN: ADR 0007 decisions — schema fields, password hashing, Google OIDC + PKCE, session `method`, temporary-password gate, two new limiters, admin reset/unlink, sign-in page, change-password page, VI/EN messages, docs.
- Scope OUT: ADR 0006 roles (`role` field, `can`), MFA, self-service password reset, password signup, operator UI, privacy notice copy (owner input), account self-deletion.
- Evidence: `src/server/planner/auth.ts`, `repository.ts:182` (`identify`), `:219` (`signIn`), `:286` (`createUser`), `http.ts:107` (`requireSameOrigin`), `:203` (`plannerRoute`), `store.ts` (`PlannerData`), `src/server/rate-limit.ts`, `src/lib/return-to.ts`, `src/app/[locale]/sign-in/page.tsx`, `src/components/planner/sign-in-form.tsx`.
- Constraints / dependencies: no new runtime dependency (`node:crypto`, `fetch` only); `tokenHash` stays required — a Google-created user gets an access token that is generated and discarded (the operator can rotate it later); every new field optional so existing `.data/planner.json` loads.
- Architecture decision / ADR: [ADR 0007](../../docs/adr/0007-password-and-google-sign-in.md), accepted 2026-11-10.
- Interface contract:
  - `POST /api/planner/session` body `{ accessToken }` | `{ email, password }` → 201 `{ user, expiresAt, mustChangePassword }`.
  - `POST /api/planner/password` `{ currentPassword, newPassword }` → 204; kills the user's other sessions.
  - `GET /api/planner/oauth/google/start?returnTo=&locale=` → 302; `GET /api/planner/oauth/google/callback` → 302 to `returnTo` or `/sign-in?error=<code>`.
  - `POST /api/admin/planner/users` accepts optional `email` → response adds `temporaryPassword` when given.
  - `POST /api/admin/planner/users/:userId/reset-password` → `{ user, temporaryPassword }`; `DELETE /api/admin/planner/users/:userId/google` → `{ user }`.
  - Env: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (both required to enable), `GOOGLE_SIGNUP_ENABLED` (default true), `NEXT_PUBLIC_SITE_URL` (redirect URI base; falls back to the request origin).
- Tasks by owner: Architect — ADR + this contract (done). BE — schemas, password/google modules, repository, routes, tests. FE — sign-in page, change-password page, messages. Implemented in the main session in dependency order (BE then FE), files disjoint.
- File ownership: BE `src/server/**`, `src/app/api/**`, `tests/planner-password*.test.ts`, `tests/planner-google*.test.ts`; FE `src/app/[locale]/**`, `src/components/planner/**`, `messages/*.json`, `src/i18n/routing.ts`, `src/lib/return-to.ts`.
- Acceptance criteria / tests: the test list in ADR 0007 Follow-up; `typecheck`, `lint`, `test`, `build` pass.
- Security and migration risks: OIDC checks (state one-use, nonce, PKCE, signature, iss/aud/exp, email_verified); user enumeration; CSRF on the new POSTs (enforced by `plannerSessionRoute`/`plannerRoute`); PII in `.data/planner.json`. `security` review recommended — NOT RUN unless the user asks.
- Rollback approach: revert the PR; the new fields are optional and ignored by the old code, access tokens unchanged.
- Budget: main session only, no subagents; stop if a check fails twice on the same cause.
- Security review (2026-11-10, on the user's request): PASS_WITH_WARNINGS. Both MEDIUM findings fixed in the same branch — (1) no Google linking by email: an email match answers `link_required`; linking is explicit from a signed-in session (`start?intent=link`, `linkGoogle`); (2) forgeable per-IP keys: global signup bucket (30/h), `MAX_LIVE_OAUTH_ATTEMPTS` = 500, scrypt concurrency gate (4 active / 32 waiting → 429). LOW findings open: per-account limiter can throttle a victim's password sign-in; temporary passwords never expire; no timeout on Google fetches; redirect URI falls back to the request origin without `NEXT_PUBLIC_SITE_URL`.
- Security re-review (cycle 2, 2026-11-10): PASS_WITH_WARNINGS; both earlier MEDIUMs confirmed fixed. One new MEDIUM fixed on the user's go-ahead: `dummyPasswordHash` cached a promise that could reject while the scrypt gate was full, making unknown emails answer 429 against 401 for known ones; it is now built synchronously from random bytes, uncached. New LOWs, accepted: the link callback does not re-check the temporary-password flag (resets delete sessions, so unreachable in practice); a signup slot is spent even if the write then fails. Also fixed: the password HTTP tests timed out under full-suite load at the production scrypt cost (30 s timeout on those describes). Review cycles exhausted — further changes go to the user.

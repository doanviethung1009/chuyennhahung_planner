  - Limiter (PR 3): `AsyncRateLimiter { check(key): Promise<RateLimitResult> }` beside the sync `RateLimiter`; table `rate_limit_counters (key, window_start, count)` primary key `(key, window_start)`; one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING count` on the pool **outside** the store transaction (avoids the advisory lock, `postgres-planner-store.ts:10-17`); opportunistic sweep of old windows; fixed window (≤2× at a boundary, accepted). - Security and migration risks:
  - One DB round trip per limited write; the Postgres VM is separate, latency **unmeasured** (assumption: LAN hop). Fallback if too costly: ADR 0019 option D with a persisted counter only for the few paths that matter.
  - Fixed window can pass up to 2× the limit at a boundary; accepted for abuse control, not for quotas.
  - The audit log is **personal data** (actor ids; reasons may quote user text): 1-year retention with a sweep, never logged elsewhere, covered by the owner's privacy statement (P11-D1), no raw guest key, no email.
  - Regression risk refactoring moderation methods: mitigated by criterion 3 and by doing P10-14 first; keep changes inside the transaction callbacks.
  - Two limiter interfaces coexist; a test must keep each call site on the intended one.
  - **`x-forwarded-for` spoofing is not fixed by a shared store.** nginx overwrite is tested in-repo (`tests/deploy-config.test.ts`) but the real VM config and any Cloudflare Tunnel in front are unconfirmed (P10-12, open question 2).
  - Migrations are additive (new tables only); take care that PR 2/PR 3 numbering follows merge order; a failed migration on startup is a 503 with retry backoff (`instance.ts:51-58`), so test the migration on an existing database before merging.
  - Limiter fail-closed means a DB outage blocks review writes — same database as the write itself, so no extra user-visible failure.
- Rollback approach: remove the calls from the repository and the module `submission.ts`; the repository reverts to its inline checks (the old code is in git); drop `rate_limit_counters` and `audit_events` with the rollback SQL files (manual, `db/rollback/`); the review routes return to the in-memory limiters. Events already stored sit inert. JSON store: the extra `auditEvents` key is ignored on read by older code only if the schema is not `.strict()` for it — rolling the code back past PR 2 requires exporting with the older `documentSchema`, so keep a rollback note in the feature document.

# Task Contract: admin-role-bootstrap — ADR 0006 migration steps 1–2
- Class: L (new trust-relevant field and a privilege-granting route; no UI)
- Desired outcome / user impact: the user model carries a role; an operator holding `ADMIN_API_TOKEN` can create or promote the first `admin`. Nothing user-visible changes: no request path enforces a role yet.
- Scope IN: optional `role` on the stored user; resolved `role` on the public user and on `PlannerIdentity`; pure `src/server/identity/permissions.ts`; `role` on `POST /api/admin/planner/users`; new `PATCH /api/admin/planner/users/[userId]`; Google first sign-in sets `role: 'member'`; tests; docs.
- Scope OUT: `auditEvents` store, admin UI/portal, session-path admin routes, role-based session expiry, MFA, any identity provider, removing browser use of the token (ADR 0006 steps 3–4, Phase 07). Calling `can` from any route.
- Evidence: `src/server/planner/schemas.ts:120` (`plannerUserSchema`), `:~140` (`publicPlannerUserSchema`), `src/server/planner/auth.ts:53` (`PlannerIdentity`), `repository.ts:236` (`identify`), `:2005` (`toPublicUser`), `:518` (Google create), `:629` (operator create), `src/app/api/admin/planner/users/route.ts`, `users/[userId]/{route,rotate-token,reset-password,google}`.
- Constraints: no new dependency; field optional so existing `.data/planner.json` loads unchanged; the admin token never becomes an identity in `plannerRoute`.
- Architecture decision / ADR: [ADR 0006](../../docs/adr/0006-unified-identity-and-roles.md), accepted 2026-11-11 for steps 1–2 only.
- Interface contract:
  - `plannerUserSchema.role: z.enum(['member','editor','admin']).optional()`. Absent reads as `member`. Read-default lives in ONE helper `userRole(user): Role` (in `permissions.ts`, importing nothing from planner); `toPublicUser` and `identify` both call it. Stored rows are never rewritten by a read. `publicPlannerUserSchema` makes `role` required (`.extend({ role: roleSchema })`) so it always returns the resolved value. Define `roleSchema`/`Role` once in `permissions.ts`; schemas.ts imports it.
  - `PlannerIdentity.role: Role` (required, resolved), set in `identify` on the cookie path and the bearer path from the user row. Any other code constructing a `PlannerIdentity` (tests, helpers) must supply it.
  - `permissions.ts` (pure, no I/O): `type Role`; `type Action = 'user:provision' | 'user:promote' | 'template:write' | 'story:publish' | 'trip:support-read'`; static `ROLE_ACTIONS: Record<Role | 'service', readonly Action[]>`; `can(principal: { role: Role | 'service' }, action: Action): boolean`. Map: `member` → none; `editor` → `template:write`, `story:publish`; `admin` → editor's plus `user:provision`, `user:promote`; `service` → `user:provision`, `user:promote`, `template:write`, `story:publish`. **No principal holds `trip:support-read`** (ADR decision 3: reserved name, denied to all, so a later grant is an explicit ADR). Unknown role/action → false.
  - Step 1 confirmed: nothing in the request path calls `can`; the map is exercised by tests only. Admin routes keep `adminPlannerRoute` (token) as their sole gate.
  - `POST /api/admin/planner/users`: body gains optional `role` (default `member`); response unchanged except `user.role`. Existing `email`/temporary-password behaviour untouched.
  - `PATCH /api/admin/planner/users/[userId]`: `adminPlannerRoute` only (admin token; a session cookie or no token → 401 via existing gate). Body `z.object({ role: roleSchema }).strict()` — `.strict()` yes: an unknown key (e.g. `email`, `tokenHash`) must be a 422, not silently ignored, because this route grants privilege. Responses: 200 `{ user }` (public user, same envelope as sibling routes) ; 422 `validation_failed` on bad/missing/extra body (amended: matches sibling admin routes); 401 on missing/wrong token; 404 `not_found` unknown user. Idempotent: same role again → 200, no write beyond `updatedAt` being left unchanged (do not bump when unchanged). Demotion allowed; no "last admin" guard (the token can always re-promote). Existing sessions are not revoked (role is read per request in `identify`, so a change takes effect immediately).
  - Google first-sign-in create (`repository.ts:~518`) writes `role: 'member'` explicitly; `createdVia: 'google'` can never confer a role.
- Tasks by owner: Architect — ADR flip + this contract + architecture note (done). BE — everything below. FE — none. QC/Security — on demand.
- File ownership: backend-engineer owns all `src/**` and `tests/**` for this task: `src/server/identity/permissions.ts` (new), `src/server/planner/{schemas,auth,repository}.ts`, `src/app/api/admin/planner/users/**`, `tests/identity-permissions.test.ts`, `tests/planner-admin-roles.test.ts`, plus `.claude/context/project-context.md` module map. Architect owns ADR + `docs/architecture.*`. No frontend files are touched.
- Acceptance criteria / tests (write explicitly; each is an invariant, not coverage padding):
  1. Legacy user row without `role` → `toPublicUser` returns `role: 'member'` and `identify` returns `role: 'member'`; the stored row is unchanged.
  2. `identify` returns the stored role on the cookie path AND on the bearer path (editor/admin fixtures).
  3. `can` matrix over every role×action: `member` none; `admin` denied `trip:support-read`; `service` denied every `trip:*`; no role/service allowed `trip:support-read`; unknown role → false.
  4. PATCH: 200 promote and idempotent repeat; 404 unknown id; 401 with no token, wrong token, and with a valid member session cookie (no token); 422 for invalid role, missing role, and an extra key (`.strict()`).
  5. POST create with `role: 'admin'` persists it; omitted → `member`; invalid → 422.
  6. Admin token still cannot read any trip (existing trip routes reject it; an admin-role session gets `not_found` on another member's trip).
  7. Public user JSON never contains `tokenHash`, `passwordHash`, `googleSub` — on create, PATCH, list and Google-created users.
  8. Google first-sign-in user has `role: 'member'`.
  Plus `typecheck`, `lint`, `test`, `build` with output stated.
- Security and migration risks: PATCH is the first route that grants privilege; it rests entirely on the token gate (rate limit and timing-safe compare already in `adminPlannerRoute`). Nothing reads role for authorization yet, so a wrong role has no effect today — the risk is a future step trusting it. `security` review recommended (trust-boundary change) — NOT RUN unless the user asks; `qc` worth running.
- Rollback approach: revert the PR; `role` is optional, old code ignores it, tokens and sessions unchanged.
- Budget: backend-engineer one invocation; stop if a check fails twice on the same cause.

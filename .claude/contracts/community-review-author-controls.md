# Task Contract: community-review-author-controls — Staff ask the author / switch off a review author
- Class: L (additive on the shipped ADR 0014 trust boundary; new table + status value on both stores; new staff permission; no new public surface). Over XL's "human approval at risky boundaries" only at the ADR gate below.
- Desired outcome / user impact: staff can pause a review and put a question to its Planner author (author answers by editing), and can mute an author (Planner account, or a guest key) for one place or everywhere, reversibly and with an audit trail — without exposing any author id, key or email.
- Scope IN / OUT:
  - IN: status `held`; `decision: 'hold'` on the existing admin PATCH; `ReviewRestriction` entity, routes, enforcement on write and read-time hiding; action `community:restrict`; author-facing notice in the Planner reviews panel; admin UI (hold button, restrictions list, mute/lift); migration `0007`; both stores; VI/EN strings; docs.
  - OUT: email or any mail channel, showing author email to staff, replies/threads, appeals form, notifications/badges, per-place guest switch (reading C — only if owner asks), identity-based guest enforcement, report button, `moderator` role.
- Evidence (existing files, APIs, models): ADR 0014; `.claude/contracts/community-trips-and-reviews.md`; `src/server/planner/repository.ts` (`upsertPlannerReview` ~1420, `deleteOwnReview`, `createGuestReview` ~1500, `listApprovedReviews`, `listReviewQueue`, `decideReview`, `ownReviewOf`/`publicReviewOf` ~2507); `src/server/planner/schemas.ts` (`communityReviewSchema`, `reviewStatusSchema`, `reviewDecisionSchema`, `ReviewQueueItem`, `OwnReview`); `db/migrations/0006_community_reviews.sql` (inline `status` CHECK); `src/server/identity/permissions.ts`; `src/server/rate-limit.ts` (`clientKey`); `src/app/api/admin/community/reviews/[id]/route.ts` (`adminPlannerRoute`, `actorOf`); `src/components/admin/community/review-queue.tsx`; `src/components/reviews/place-reviews-panel.tsx`; `src/content/site.ts` (`contribution`, still `null`).
- Constraints / dependencies: no mail, no invented contact (rule 8); `takedownContact` is owner data and still missing, so the author notice shows none until set; no foreign keys; public projections `PublicCommunityReview` / `CommunityTripCard` unchanged; the removed/rejected-cannot-be-overwritten rule stays; Vietnamese-first, VI/EN parity, a11y (≥44px, real buttons); public pages must not import repository (`tests/client-boundary.test.ts`); next migration number is `0007`.
- Architecture decision / ADR (if needed): [ADR 0015](../../docs/adr/0015-community-review-author-controls.md) — **Proposed; owner must accept and answer its 7 questions before code.**
- Interface contract (API, types, DB):
  - `PATCH /api/admin/community/reviews/[id]` `{decision:'approve'|'reject'|'remove'|'hold', reason}` — `hold` only for `source:'planner'` + `approved`, needs `reason` (the question); action `community:moderate`.
  - `POST /api/admin/community/restrictions` `{reviewId, scope:'place'|'all', reason, expiresAt?}` → 201 `{id}`; guest subject requires `expiresAt` ≤ 90 days (default 30), refused when key = hash of `'unknown'`; 409 if an equal active restriction exists; 403 if the target account holds `community:moderate`. `GET …/restrictions?active=` (list, staff-only shape, no ids of authors/keys); `DELETE …/restrictions/[id]` (idempotent lift). Action `community:restrict` (admin, service).
  - Types in `schemas.ts`: `reviewStatusSchema` + `'held'`; `reviewRestrictionSchema` `{id, subject:'user'|'guest', authorId|null, guestKey|null, placeSlug|null, reason, createdAt, createdBy, expiresAt|null, liftedAt|null, liftedBy|null}`; `OwnReview.restriction?`; `ReviewQueueItem.restricted`, `.restrictionId`.
  - Repository: `holdReview` (via `decideReview`), `createRestriction`, `liftRestriction`, `listRestrictions`; private `activeRestrictions(data, at)` used by `upsertPlannerReview`, `createGuestReview` (refuse `forbidden` 403), `listApprovedReviews`/average/home strip (filter). `upsertPlannerReview` on `held` → `approved`, note cleared. `deleteOwnReview` still allowed under a restriction, not on `removed`.
  - DB: `db/migrations/0007_review_author_controls.sql` (drop + re-add `community_reviews_status_check` with `held`; `CREATE TABLE review_restrictions`, indexes on `author_id`, `guest_key`); rollback `db/rollback/0007_…sql` (manual, first convert `held` rows). JSON key `reviewRestrictions`; mirror in `planner-rows.ts`, `planner-transfer.ts`, `store.ts`, `tests/planner-pg-fixtures.ts`.
  - Rate limit: new per-principal staff-write limiter (60/h) on hold, restriction create/lift.

- Acceptance criteria / tests:
  1. `hold` hides a Planner review from public reads and the average; a guest review cannot be held (409); `reason` required.
  2. Author edit on a `held` review republishes it (`approved`, note cleared); on `removed`/`rejected` still 409 (security-review rule intact).
  3. Restriction scope `place` blocks writes and hides reviews only for that place; `all` for every place; other authors unaffected; lifting restores hidden reviews without any row rewrite; an expired restriction is inactive.
  4. Blocked Planner write → 403 `forbidden`; blocked guest write → 403 with no key or address in the body; honeypot behaviour unchanged.
  5. Guest restriction: requires `expiresAt` ≤ 90 days; refused for `'unknown'` key; staff responses and queue never contain `authorId` of a guest key, `guestKey`, email.
  6. `can` matrix: `member` 403 on moderate and restrict; `editor` passes hold but gets 403 on restrict; `admin`/`service` pass; cannot restrict a user who holds `community:moderate`.
  7. Public projection tests (`PublicCommunityReview`, `CommunityTripCard`) pass **unchanged**; own-review projection exposes the reason and restriction to the author only.
  8. Each staff write is rate-limited and rejected cross-origin for a cookie session (ADR 0010); `decidedBy`/`createdBy`/`liftedBy` recorded.
  9. JSON/PostgreSQL parity incl. migration on an empty and an existing DB; deleting the account deletes its reviews and restrictions.
  10. VI/EN parity (`tests/i18n.test.ts`), docs tests, `typecheck`, `lint`, `test` pass with output stated.
- Security and migration risks: staff abuse of a new person-level power (reasons, actor log, `community:restrict` split, expiry for guests); guest key forgeable/shared (time-box, refuse `'unknown'`, warn about shared addresses); `guest_key` is a reversible IPv4 hash — keep out of every response and log; evasion by a second account accepted; altering a CHECK constraint on a live table (additive but take it in a transaction; confirm the constraint name on the real DB); no new public field, no new unauthenticated endpoint.
- Rollback approach: remove routes/UI; stored `held` status and `review_restrictions` stay inert; manual rollback SQL must first move `held` → `approved`/`removed`, then restore the CHECK and `DROP TABLE review_restrictions`.
- Budget: 0 subagents; stop condition = owner accepts ADR 0015 and answers its questions; then PR 1, PR 2 after PR 1 merges. Estimate: PR 1 ≈ M (≈ 8–10 files, one migration), PR 2 ≈ L (≈ 18–22 files incl. tests); about 1.5× the size of the original reviews PR together.
